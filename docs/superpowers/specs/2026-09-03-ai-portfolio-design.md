# AI Portfolio Website — Design

## Purpose

GitHire will turn a candidate's existing CV data and public GitHub signals into an editable, publishable portfolio website. The portfolio gives recruiters and other visitors one public URL where they can inspect the candidate's story, experience, selected work, and GitHub-backed skills.

The feature is not an automatic publishing tool. AI prepares a draft; the candidate reviews and curates it before publishing, and can continue editing after publication.

## Product position

GitHire's portfolio flow follows the simple `connect -> AI draft -> review -> publish` model, while remaining distinct from generic portfolio generators:

- CV, GitHub, verified skills, and job matching already exist in GitHire.
- GitHub-backed skills are explicitly labeled as verified only when they have existing commit evidence.
- The public portfolio stands on its own outside GitHire, so candidates can reuse the same link in any job portal, application, or professional profile.

The user-facing value proposition is: **turn CV and GitHub coding evidence into a public, recruiter-ready portfolio.**

## Scope

### Included in MVP

- One candidate-owned portfolio per account.
- Automatic opaque public ID, exposed at `/p/{public_id}`; no username choice in MVP.
- AI-assisted draft generation from the candidate's stored CV data and GitHub signals.
- A mandatory review/edit stage before first publication.
- Editable content after publication; candidates choose whether a save remains draft-only or updates the stable public URL.
- Publish and unpublish controls.
- Three curated themes using the same portfolio content:
  - `editorial`: narrative-first personal brand.
  - `developer`: project and GitHub-proof first.
  - `professional`: clean recruiter-first presentation.
- A public, unauthenticated portfolio page that returns only curated public data.
- Candidate controls for opt-in contact links and section visibility.
- Up to six selected GitHub repositories, instead of exposing every repository automatically.
- Indonesian or English AI copy, selected before generation.
- Optional candidate-uploaded photo with an initial avatar fallback.

### Excluded from MVP

- Custom domains, portfolio analytics, heatmaps, contact forms/inboxes, SEO tooling, and visitor tracking.
- A drag-and-drop page builder or arbitrary section layouts.
- More than three themes.
- Multiple portfolio sites or portfolio version history.
- Direct publication or download of CV PDFs or unreviewed source data.

## Data model

Add a `Portfolio` model linked one-to-one with `User`, rather than putting publication fields on `CandidateProfile`. This preserves the raw CV/GitHub profile as the private source of truth and makes the public payload an explicit candidate-curated projection.

Proposed fields:

- `id`: UUID primary key.
- `user_id`: unique foreign key to `users`.
- `public_id`: unique, opaque URL-safe ID generated by the server.
- `status`: `draft` or `published`.
- `draft_content`: the candidate's latest editable JSON content, including theme and language.
- `published_content`: a snapshot of the last candidate-approved public version, including a server-owned verified-skill snapshot.
- `draft_photo` and `published_photo`: separate bounded image snapshots so draft changes do not alter the live page.
- `published_at`, `created_at`, `updated_at`.

The existing `CandidateProfile` remains the private source for `cv_data`, `github_signals`, `merged_skills`, `verified_skills`, and biodata. A public response is assembled from `Portfolio.content` plus only the explicitly selected or safe derived GitHub/verification fields.

The schema change must be represented in `models.py` and with idempotent DDL in `main.py`, following the project's no-Alembic convention.

## Backend API

Authenticated candidate endpoints under `/me/portfolio`:

- `POST /me/portfolio/generate`: builds or refreshes a draft from currently stored CV and GitHub data. It must not publish and requires both usable CV data and GitHub data.
- `GET /me/portfolio`: returns the candidate's complete editable draft/status.
- `PATCH /me/portfolio`: validates and persists candidate edits, selected repositories, visibility options, and theme.
- `POST /me/portfolio/publish`: validates minimum displayable content, sets `published`, and returns the stable public URL.
- `POST /me/portfolio/unpublish`: changes status back to `draft`; the public URL stops serving the profile.
- `POST|GET|DELETE /me/portfolio/photo`: manages the candidate's optional draft photo.

Unauthenticated endpoint:

- `GET /portfolios/{public_id}`: returns a deliberately filtered public view only for a published portfolio. Unknown, unpublished, or malformed IDs return 404 without revealing account state.

All authenticated calls use the existing `get_current_user` pattern. The public endpoint has no Clerk dependency. No raw `CandidateProfile` object or original CV file is ever returned publicly.

## Draft generation

The generator is deterministic wherever possible:

- Candidate name, experience, education, certifications, declared skills, and links originate from existing `cv_data` and approved biodata.
- Repository choices originate from stored `github_signals.repos_detail`; the candidate chooses at most six.
- For selected repositories, GitHire fetches a bounded public README and asks Gemini for an editable summary. README text is untrusted evidence, never executable instructions.
- Verified skill labels use only existing `verified_skills`; no new verification claim is inferred by the portfolio generator.
- AI writes the initial headline, bio, and project summaries in the selected Indonesian or English language. It must not invent experience, outcomes, or credentials. If AI is unavailable, an editable deterministic draft is still created.

## Frontend flow

Add the protected candidate route `/dashboard/portfolio` and link it from the candidate dashboard navigation/profile surface.

1. A candidate with synced data selects **Create portfolio**.
2. GitHire generates a private draft and opens the editor.
3. The editor presents sections, not a freeform canvas: identity, optional photo, story, selected work, skills/proof, experience/education, and opt-in contact links.
4. The candidate picks one of the three themes; the public renderer applies that theme to the same reviewed content.
5. **Publish** exposes the stable `/p/{public_id}` link. The interface offers copy-link and unpublish actions.
6. After publish, edits can remain a private draft or replace the public snapshot at the same URL.

The dashboard editor uses the established Workbench visual language. The public presentation can use theme-specific styling and must not be constrained to dashboard-card aesthetics.

## Public page

`linkify/src/app/p/[publicId]/page.tsx` is a server-rendered public route that fetches the public backend endpoint. It renders the selected theme with the same information architecture:

- Hero: optional photo or initial avatar, name, headline, short story, and allowed contact links.
- Selected work: curated GitHub projects with repository/demo links and stack.
- Skills: declared skills and clearly separated GitHub-verified skills.
- Experience, education, and certifications only when enabled by the candidate.
- GitHub proof: succinct repository/language/stat evidence rather than decorative charts or an in-product recruiter call to action.
- A subtle `Created with GitHire` footer and `noindex, nofollow` metadata.

The route must handle a 404 gracefully with a neutral unavailable page. It must not require Clerk, leak dashboard controls, private contact details, CV files, birth details, addresses, or unselected repositories.

## Safety and validation

- Server generates and validates `public_id`; clients cannot choose or overwrite it.
- Patch payloads are Pydantic validated with field and list-size limits.
- Theme/status values are enum constrained.
- Repository links must be selected from the candidate's stored GitHub repository data or validated GitHub URLs; arbitrary scriptable URLs are rejected.
- Public contact fields are opt-in. Private fields remain private by default; there is no contact form.
- Candidate prose is editable, but verified badges and repository proof fields are always server-derived.
- Publish requires at least a display name or headline and one meaningful evidence/content section; otherwise the API returns actionable validation errors.
- Syncing CV/GitHub does not overwrite a published portfolio. The candidate explicitly regenerates/reviews updates.
